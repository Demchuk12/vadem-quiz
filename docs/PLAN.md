# Квіз для друзів: план реалізації

Веб-застосунок у стилі «Своя гра» (Jeopardy). Ведучий керує, друзі підключаються з телефонів і відповідають у реальному часі. Ведучий також транслює екран у Discord.

## 1. Стек

- **Frontend:** Angular (standalone components, signals), TypeScript, PWA-friendly верстка (mobile-first для гравців).
- **UI-бібліотека:** **Vadem** (власна бібліотека автора). Увесь інтерфейс будується на її компонентах, сторонні UI-кіти (Angular Material, PrimeNG тощо) не підключати.
  - Перед початком роботи Claude Code має прочитати документацію/вихідний код Vadem (README, список компонентів, теми/токени, приклади використання) і використовувати наявні компоненти (кнопки, поля, модалки, таблиці, карточки тощо) замість власних.
  - Якщо потрібного компонента у Vadem немає (наприклад, велика кнопка баззера, клітинка дошки, лідерборд), його **додають у саму Vadem** (автор має доступ до бібліотеки і може випускати оновлення), а не пишуть локально в застосунку. Компонент робиться за конвенціями Vadem (токени, теми, API), після чого застосунок оновлює залежність і використовує його.
  - Порядок роботи: Claude Code складає список відсутніх компонентів, автор додає/оновлює їх у Vadem (або Claude Code робить це в репозиторії Vadem, якщо дано доступ), далі застосунок підтягує нову версію.
  - Тема, кольори, типографіка та відступи беруться з дизайн-токенів Vadem.
  - Підключення: `TODO: назва npm-пакета / шлях до репозиторію / версія`.
- **Backend:** Supabase (Postgres + Realtime + Storage + RPC-функції). Свого сервера немає.
- **Деплой:** Vercel (статичний Angular build).
- **Картинки:** Supabase Storage (див. розділ 6).

## 2. Ролі

- **Ведучий (host):** створює кімнату, завантажує/редагує квіз, відкриває питання, відкриває «баззер», ставить «правильно/неправильно», вручну коригує очки, завершує гру.
- **Гравець (player):** заходить за кодом кімнати + вводить нікнейм. Бачить дошку, поточне питання, свій рахунок, таблицю лідерів, велику кнопку відповіді. Керування немає.
- Один застосунок, різні маршрути: `/host/:room`, `/play/:room`, `/join`.

## 3. Ігровий процес

1. Ведучий створює кімнату, отримує код (4–5 символів) і секретний host-токен (зберігається в localStorage ведучого).
2. Гравці заходять за кодом, з'являються в лобі.
3. **Дошка:** N категорій × 5 питань (200, 400, 600, 800, 1000). Зіграні клітинки позначаються.
4. Ведучий обирає клітинку → стан `question_shown`: усі бачать текст/картинку питання. Кнопки гравців **заблоковані**, поки ведучий читає.
5. Ведучий натискає «відкрити відповіді» → стан `buzzing_open`: кнопки активні.
6. Перший, хто натиснув, фіксується **сервером** (атомарно). Решта блокуються. Ведучий бачить, хто перший.
7. Ведучий ставить:
   - **Правильно:** гравцю `+очки`, клітинка закривається, показується правильна відповідь.
   - **Неправильно:** гравцю `−очки`, баззер відкривається для інших (цей гравець у цьому питанні вже не може).
   - **Ніхто не відповів / пропустити:** клітинка закривається без очок.
8. **Раунди: три, однакова механіка.** Після кожного раунду показується рахунок і таблиця лідерів, ведучий переходить до наступного. Вартість питань залежить від номера раунду:
   - Раунд 1 (множник ×1): 200, 400, 600, 800, 1000
   - Раунд 2 (множник ×2): 400, 800, 1200, 1600, 2000
   - Раунд 3 (множник ×3): 600, 1200, 1800, 2400, 3000
   - Тобто `очки = базова вартість (200..1000) × номер раунду`. Базова вартість і множник зберігаються окремо, щоб легко змінити схему. Кількість раундів і множники налаштовуються в квізі.
9. Ручна корекція очок будь-якого гравця в будь-який момент.

## 4. Модель даних (Postgres)

- `quizzes` (id, title, owner_token_hash, created_at)
- `categories` (id, quiz_id, round, position, title)
- `questions` (id, category_id, points, text, image_path nullable, answer_text, answer_image_path nullable, position)
- `rooms` (id, code, quiz_id, host_token_hash, state, current_question_id, buzz_winner_player_id, round, created_at)
- `players` (id, room_id, nickname, score, joined_at, connected)
- `room_questions` (room_id, question_id, status: unplayed/played, resolved_at)
- `answers_log` (id, room_id, question_id, player_id, correct bool, delta, created_at) для історії та відкату

Realtime підписка на `rooms`, `players`, `room_questions`.

## 5. Баззер і безпека

- Гравець не пише в таблиці напряму. **Усі дії йдуть через RPC-функції** (`security definer`) в Postgres.
- `buzz(room_id, player_id)`: у одній транзакції перевіряє `state = 'buzzing_open'` і `buzz_winner_player_id is null`, виставляє переможця одним `UPDATE ... WHERE buzz_winner_player_id IS NULL`. Перший виграє, решта отримує відмову.
- Дії ведучого (`open_question`, `open_buzz`, `judge`, `adjust_score`, `close_question`) перевіряють host-токен (порівняння з хешем у `rooms`).
- RLS: гравці тільки читають; запис заборонений напряму.
- **Тексти відповідей не віддавати гравцям до відкриття.** Тримати `answer_text` в окремій таблиці/представленні, недоступному anon-ролі, або віддавати через RPC лише після рішення ведучого.
- Рейт-ліміт і захист від подвійних натискань на клієнті та в RPC.
- Опційно: штраф за передчасне натискання (до `buzzing_open`).

## 6. Картинки і сховище

- Supabase Storage, приватний бакет `quiz-media` або публічний із непередбачуваними іменами файлів.
- **Стиснення на клієнті перед завантаженням:** WebP, довша сторона до ~1280 px, якість ~80 (≈100–250 КБ). Це в рази економить місце й трафік.
- Ліміти безкоштовного плану: 1 ГБ файлів, 5 ГБ egress на місяць, проєкт «засинає» після тижня простою. Pro ($25/міс): 100 ГБ файлів, 250 ГБ egress.
- Якщо потрібно більше місця без підписки, альтернатива: Cloudflare R2 (великий безкоштовний ліміт, без плати за egress), а в БД зберігати лише URL.
- Прелоад картинки поточного питання на пристроях гравців, щоб показ був миттєвим.

## 7. Екрани

**Ведучий:** редактор квізу (категорії, питання, картинки), лобі (список гравців, код/QR), дошка з клітинками, панель питання (текст, відповідь, таймер, «відкрити відповіді», «правильно/неправильно/пропустити»), таблиця очок з ручною правкою.
**Гравець:** вхід (код + нікнейм), лобі, дошка (лише перегляд), екран питання, велика кнопка відповіді (стани: заблокована / активна / «ти перший» / «вже відповів»), рахунок і лідерборд.
**Режим для стріму:** окрема чиста сторінка з дошкою та питанням без панелі керування, зручна для Discord share.

## 8. Нефункціональні вимоги

- Затримка баззера мінімальна: один виклик RPC, без зайвих запитів перед натисканням.
- Перепідключення гравця після втрати зв'язку (повернення в ту саму кімнату за нікнеймом/збереженим player_id).
- Синхронізація годинників не потрібна, бо переможця визначає сервер.
- Мобільна верстка: велика кнопка, жодних випадкових скролів/зумів, вібрація при натисканні.

## 9. Етапи

1. **Каркас:** Angular-проєкт, маршрути, підключення Supabase, міграції БД.
2. **Кімнати й гравці:** створення кімнати, вхід за кодом, лобі в реальному часі.
3. **Редактор квізу:** категорії/питання, імпорт/експорт JSON, завантаження картинок зі стисненням.
4. **Ігровий цикл:** дошка, відкриття питання, баззер (RPC), судження, очки.
5. **Полірування:** режим для стріму, звуки, анімації, перепідключення, таймер.
6. **Деплой** на Vercel, тест із друзями.

## 10. Відкриті питання

- Раунди: 3 (множники ×1, ×2, ×3), питання в кожному раунді свої, нові категорії. Фінальне питання зі ставками поки не потрібне (уточнити).
- Таймер на відповідь? На читання?
- Чи зберігати квізи між іграми (так, у `quizzes`) і ділитися ними?
- Скріни оригінального формату, щоб повторити вигляд дошки.
- Vadem: як її підключати (npm-пакет, git-репозиторій чи локальний шлях), яка версія Angular підтримується, де документація, які компоненти вже є.
